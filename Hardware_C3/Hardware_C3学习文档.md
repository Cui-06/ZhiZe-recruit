# Hardware_C3 学习文档

## 一、学习背景

`Hardware_C3` 题目要求为：
- 初始状态：电机静止，蜂鸣器不发声，OLED 熄灭，数码管熄灭。
- 使用按键矩阵或组合键实现 5 位号码输入和拨号，号码在数码管上显示。
- 输入 120 之后按下拨号 Key，开始通信，通信过程如下（其中 PC 向单片机发送部分可手动操作）：
  拨号 Key 被按下 →
      1. 单片机向 PC 发送” 需要救援”
      2. PC 向单片机回复” 报告位置”
      3. 单片机回应位置”01”
      4. PC 回复” 收到”
  → 电机高速正转，蜂鸣器持续发出滴露滴露，OLED 滚动显示字样
- 一段时间后电机停转，蜂鸣器停止发声，0LED 熄灭，数码管熄灭。

后期实物调试时，原来的电机驱动方案不稳定，因此改换为 D153C TB6612 双路驱动稳压模块，并搭配 MG310 霍尔编码器电机。

## 二、工程结构

`Hardware_C3` 仍然采用 `User` 和 `Driver` 分层：

```text
Hardware_C3
├─ User
│  ├─ main.c
│  ├─ Listings
│  └─ Objects
└─ Driver
   ├─ MatrixKey.c / MatrixKey.h
   ├─ Seg.c / Seg.h
   ├─ Uart.c / Uart.h
   ├─ Motor.c / Motor.h
   ├─ Encoder.c / Encoder.h
   ├─ Beep.c / Beep.h
   └─ OLED.c / OLED.h
```

主程序 `main.c` 负责系统初始化、号码输入处理、串口通信状态机和救援流程控制。矩阵键盘、数码管、串口、电机、编码器、蜂鸣器和 OLED 的底层操作放在 `Driver` 中，方便单独调试某一个模块，也避免主程序里堆积过多 IO 细节。

## 三、学习过程

最开始先把题目拆成几个相对独立的模块：矩阵键盘负责号码输入，数码管负责显示输入内容，串口负责和 PC 通信，电机、蜂鸣器和 OLED 负责通信完成后的救援提示，定时器负责软件 PWM、蜂鸣器音调切换和救援持续时间计时。

号码输入部分先完成矩阵键盘扫描和数码管显示。矩阵键盘独占 P1 口，避免扫描时反复写整个 P1 端口而影响其他模块。输入号码保存在 `Phone_Num[]` 中，`Phone_Count` 记录当前位数，数码管读取显示缓冲 `Seg_Buf[]`，主循环持续动态刷新。

串口部分使用 9600 baud、8 数据位、1 停止位、无校验。串口中断只负责把收到的字节写入环形缓冲区，主循环再逐字节取出并推进通信状态机。这样可以稳定处理 UTF-8 中文字节，不会因为中文由多个字节组成而漏判。

电机调试占用了较多时间，过程大致分为“原方案定位”和“现方案验证”两个阶段。

原方案阶段，电机驱动板、OLED 和 8051 一度共用开发板的 5 V 供电。串口收发、蜂鸣器和 OLED 单独测试都正常，但进入救援流程后，电机一启动，OLED、数码管和单片机一起熄灭或复位。为了确认执行顺序，曾临时把启动拆成两步：先开 OLED 和蜂鸣器，再延时开电机；结果前三者先正常，电机启动瞬间全部消失。这说明通信状态机已经走到启动分支，主要故障是电机启动电流把 5 V 逻辑电源拉低，而不是“收到”没有匹配。

随后把电机改用外部电源单独供电。此时 OLED 和蜂鸣器能够保持工作，但电机仍不转，说明问题还包括驱动板的 STBY、PWM、方向脚、通道选择和电机绕组接线。通过短时间直连确认电机本体可以转动，再逐项检查驱动输入和 AO1/AO2 输出，排除了电机本体损坏；电机曾经出现的震动感则提示驱动信号或启动供电仍不稳定。

最终改用 D153C TB6612 双路驱动稳压模块和 MG310 霍尔编码器电机：7.4 V 外部电源只给 D153C 和电机侧供电，8051 继续通过电脑 USB 接口供电，OLED 再由 8051 的 VCC/GND 供电。电机由 TB6612 的 AO1/AO2 输出驱动，编码器信号接 P3.2/P3.3，STBY 保持高电平。实物测试中去掉 D153C GND 到 8051 GND 的额外连接后系统正常工作。现方案中高速档软件 PWM 占空比为 7/10，通信完成后电机、蜂鸣器和 OLED 同时启动，救援计时结束后统一关闭。

这段调试的关键经验是：先用串口回执确认程序状态，再用分阶段启动区分“程序未执行”和“电源在电机启动时复位”；直连只能用于确认电机本体，不能代替驱动板测试；更换驱动板和电机后，必须重新核对电源输入、逻辑电源、公共参考地、STBY、PWM、方向脚和电机绕组线。

## 四、实现功能总结

当前 `Hardware_C3` 实现的主要功能如下：

- 上电后电机停止。
- 上电后蜂鸣器关闭。
- 上电后 OLED 关屏。
- 上电后数码管熄灭。
- 矩阵键盘最多输入 5 位号码。
- 数码管实时显示已经输入的号码。
- 输入 `120` 后按 S16 拨号，单片机向 PC 发送“需要救援”。
- PC 回复“报告位置”后，单片机返回 `01`。
- PC 回复严格匹配的“收到”后，电机、蜂鸣器和 OLED 同时启动。
- 救援状态下，电机高速正转，蜂鸣器发出双频“滴露滴露”，OLED 从右向左滚动显示“急救请避让”。
- 达到设定时间后，电机、蜂鸣器、OLED 和数码管全部关闭，通信状态回到初始状态。

当前主要引脚分配为：

| 模块 | 引脚 |
| --- | --- |
| 矩阵键盘 8 根行列线 | `P1.0~P1.7` |
| 单片机 RXD / USB-TTL TXD | `P3.0` |
| 单片机 TXD / USB-TTL RXD | `P3.1` |
| MG310 编码器 A 相 | `P3.2 / INT0` |
| MG310 编码器 B 相 | `P3.3` |
| OLED SCL | `P3.4` |
| OLED SDA | `P3.5` |
| TB6612 PWMA | `P2.1` |
| TB6612 AIN1 | `P2.6` |
| TB6612 AIN2 | `P2.7` |
| 蜂鸣器 | `P2.5` |
| 数码管段选 | `P0` |
| 数码管位选 | `P2.2~P2.4` |

TB6612 A 通道和 MG310 的接线为：

```text
P2.1 -> PWMA
P2.6 -> AIN1
P2.7 -> AIN2
STBY -> D153C 逻辑 5V 或 3V3，保持高电平
AO1  -> MG310 电机绕组线 1
AO2  -> MG310 电机绕组线 2
P3.2 -> MG310 编码器 E2A
P3.3 -> MG310 编码器 E2B
```

## 五、关键知识点总结

### 1. 矩阵键盘扫描

4×4 矩阵键盘使用 8 根线连接 16 个按键。扫描时程序依次拉低某一列，再读取各行电平，从而判断按下的位置。

矩阵键盘扫描会反复写整个 P1 口，因此 P1 不适合再接电机方向脚、OLED IIC 或其他需要稳定电平的模块。本项目把 P1 完整留给矩阵键盘，这是后期系统稳定的前提。

### 2. 数码管动态显示

八位数码管通过快速轮流点亮每一位形成稳定显示。P0 输出段码，P2.2~P2.4 通过 74HC138 选择当前显示位。

输入内容和显示动作分离：输入、删除或清空时只修改 `Seg_Buf[]`，主循环持续调用显示函数完成动态扫描。这样不会因为键盘处理或串口处理而让显示逻辑变得混乱。

### 3. UART、UTF-8 和 HEX

串口传输的本质是字节，不是“中文字符”。本项目统一按 UTF-8 字节处理中文消息。

| 内容 | HEX 字节 |
| --- | --- |
| 需要救援 | `E9 9C 80 E8 A6 81 E6 95 91 E6 8F B4 0D 0A` |
| 报告位置 | `E6 8A A5 E5 91 8A E4 BD 8D E7 BD AE` |
| 01 | `30 31 0D 0A` |
| 收到 | `E6 94 B6 E5 88 B0` |

`0D 0A` 是回车换行。当前严格匹配的目标是“收到”的 6 个 UTF-8 字节，目标数组本身不包含 `0D 0A`，所以 PC 可以只发中文对应的 6 个字节，也可以在尾部附加回车换行。

### 4. 通信状态机

通信流程：

```text
COMM_IDLE
  输入 120 并按 S16
        |
        v
COMM_WAIT_POS  等待“报告位置”
        |
        v
发送“01”，进入 COMM_WAIT_OK
        |
        v
严格匹配“收到”
        |
        v
COMM_ACTIVE  同时启动电机、蜂鸣器和 OLED
        |
        v
超时后停止并回到 COMM_IDLE
```

状态机可以防止 PC 回复顺序错误时误启动，也可以避免串口缓冲区里出现相似字节时误触发。

### 5. 定时器和协作式任务

定时器 0 中断负责几个节拍任务：调用 `Motor_Tick()` 生成软件 PWM，调用 `Beep_Tick()` 切换蜂鸣器音调，累计救援持续时间，处理删除闪烁计时。

中断里只做短小、固定耗时的工作。OLED 刷新、数码管缓冲更新和串口状态判断放在主循环中完成，这样可以避免长时间阻塞中断，系统响应也更稳定。

### 6. TB6612 H 桥与 PWM

TB6612 的 A 通道正转逻辑为：

```text
STBY = 1
AIN1 = 1
AIN2 = 0
PWMA = PWM
```

停止时程序把 AIN1、AIN2 和 PWMA 全部拉低。当前高速档占空比为 7/10，即 70%，低速和中速档分别使用 20% 和 40%。

电机不能直接由 8051 GPIO 驱动。GPIO 只提供控制信号，电机电流必须经过 TB6612，并由满足电压和启动电流要求的外部电源提供。

### 7. MG310 编码器电机

MG310 的 6 根线不是 6 根动力线，而是 2 根电机绕组线和 4 根编码器线。动力线接 TB6612 的 AO1/AO2，编码器的 VCC、GND、A 相、B 相接逻辑侧电源和单片机输入。

当前题目只要求电机高速正转，因此编码器接口已经接入，但没有参与速度闭环。若以后要做精确测速或闭环控制，还需要确认编码器线数、减速比、每圈脉冲数，并设计固定采样周期。

### 8. OLED 滚动显示

OLED 使用 P3.4/P3.5 模拟 IIC，初始化后先清屏并关闭显示。救援启动时调用 `OLED_SetScrollEnable(1)`，OLED 打开并从右向左滚动显示“急救请避让”；救援结束时关闭滚动并关屏。

滚动显示的关键是把文字位置建模清楚，并避免在启动路径中做长时间全屏清屏。当前程序通过 `OLED_Proc()` 在主循环中逐步刷新，避免收到“收到”后长时间阻塞。

### 9. 供电和地线

电机启动电流远大于空载稳态电流。若电机驱动板和 8051 都从开发板小电流 5 V 取电，电机启动时可能拉低电压，导致单片机复位或 OLED 熄灭。

本项目最后使用两路独立供电：7.4 V 外部电源只给 D153C 的 VIN/GND2 和电机侧供电；8051 由电脑 USB 接口供电，OLED 由 8051 的 VCC/GND 供电。D153C 的 5V/3V3 稳压输出没有接入 8051 或 OLED 的电源回路。

## 六、踩坑记录

### 1. 引脚冲突导致外设异常

现象：早期矩阵键盘、电机和 OLED 曾占用同一组端口，部分模块单独测试正常，合在一起就异常。

原因：矩阵键盘扫描会反复写整个端口，破坏同一端口上其他模块需要保持的电平。

修正：P1 只给矩阵键盘使用，OLED 移到 P3.4/P3.5，TB6612 控制信号移到 P2.1、P2.6、P2.7。

经验：写驱动前要先做全局引脚规划，不能只看单个模块能不能跑。

### 2. 旧方案阶段单片机掉电复位

现象：在更换驱动板和电机之前，串口通信流程可以正常完成，单片机也曾在严格匹配“收到”后返回调试回执 `OK\r\n`，但进入救援状态时外设没有持续工作。分阶段测试后发现 OLED 和蜂鸣器能先启动，而电机一启动，单片机、OLED 和数码管立即熄灭或复位。

原因：旧方案里电机启动电流太大，开发板 5 V 侧被瞬间拉低，导致单片机掉电复位。

修正：改用 D153C TB6612 双路驱动稳压模块和 MG310 电机，7.4 V 外部电源只给驱动板和电机供电，8051 由电脑 USB 供电，OLED 由 8051 供电，问题最终消失。

经验：串口在电机启动前收发正常，不能排除电机启动瞬间导致的掉电复位。判断时应观察“收到”匹配成功后数码管和 OLED 是否瞬间熄灭，并测量 8051 的 5 V 电源是否出现明显跌落。

### 3. 去掉额外 GND 跳线后恢复正常

现象：系统在去掉额外连接的驱动板电机地与 8051 地跳线后恢复正常。

原因：实物采用外部电源给 D153C 供电、电脑 USB 给 8051 供电。调试中额外连接 D153C GND 和 8051 GND 时系统不能正常工作，去掉该连接后恢复正常。

修正：按最终实物接法，不再连接 D153C GND/GND2 到 8051 GND；OLED 的 GND 只接 8051 GND。

经验：文档应记录实物验证成功的供电路径。多路供电时要明确每一路实际给谁供电，并避免把未使用的 D153C 5V 输出再接到 USB 供电的 8051 上。

## 七、收获

通过 `Hardware_C3`，我对 51 单片机多外设综合控制有了更完整的理解。相比前面的题目，C3 的难点不在某一个单独驱动，而在于串口协议、状态机、显示刷新、定时器任务、电机供电和实物接线之间的配合。

这次最重要的收获是排查问题要分层。串口能收发，不代表状态机已经进入启动条件；OLED 能显示，不代表电机供电和驱动输出正确；电机不转，也不能马上判断是代码问题。每次只改变一个变量，用串口 HEX、电压测量、最小模块测试和直连测试逐步缩小范围，才能找到真正原因。

另外，改换驱动和电机后，必须同步更新接线、代码里的 `sbit` 引脚、PWM 占空比、工程文件和文档。硬件和软件只改一边，系统都可能表现为“完全没反应”，但根因并不一定在通信流程本身。
