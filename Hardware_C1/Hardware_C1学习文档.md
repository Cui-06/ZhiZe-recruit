# Hardware_C1 学习文档

## 一、学习背景

大一下学期我曾参加蓝桥杯单片机赛道比赛并获得省级二等奖，因此对 51 单片机已有一定基础。不过当时训练使用的是封装好的竞赛开发板，各模块与单片机之间的连接关系已固定，只需参照模板和原理图调用相应驱动即可。而 Hardware_C1 则在此基础上，进一步要求自行处理电机驱动、蜂鸣器、按键、LED、数码管等模块的实际接线与引脚分配。因此，本次学习并非从零开始，而是在已有 51 基础上，将“会调用封装模块”进一步推进至“能整理底层驱动并完成综合接线调试”。

本次题目要求为：

- 使用 PWM 驱动蜂鸣器和直流电机。
- 电机实现三级调速，速度大小由 Key1 控制，方向由 Key2、Key3 控制。
- Key1 第一次按下电机低速旋转，第二次中等速度旋转，第三次高速旋转，第四次按下电机停转。
- Key2 被按下，电机为正转模式；Key3 被按下，电机为反转模式。
- 当电机高速旋转时，蜂鸣器响起滴露滴露的声音，其他时候蜂鸣器不发声。

本次学习的重点不仅在于让单个模块正常工作，更在于将多个独立实验整合为一个完整工程，并按照更清晰的工程结构进行组织：

```text
Hardware_C1
├─ User
│  ├─ main.c
│  ├─ Listings
│  └─ Objects
└─ Driver
   ├─ Key.c / Key.h
   ├─ Motor.c / Motor.h
   ├─ Beep.c / Beep.h
   ├─ Led.c / Led.h
   └─ Seg.c / Seg.h
```

这种结构将主逻辑与底层驱动分离：`User` 目录主要存放任务流程，`Driver` 目录则放置各模块的底层 `.c` 和 `.h` 文件。分层设计便于后续修改和问题排查。

## 二、学习过程

初期，我将独立按键、直流电机和蜂鸣器三个实验整合到 Hardware_C1 中。各模块在单独实验时均能正常工作，但整合后需考虑多模块同时运行的冲突问题，例如定时器资源分配、IO 引脚是否复用、各模块初始化时应处于何种状态等。

随后，根据题目要求，实现了 PWM 驱动蜂鸣器和直流电机。电机由 KEY1 循环控制速度档位：第一次按下为低速，第二次中速，第三次高速，第四次停止；KEY2 和 KEY3 分别用于设置电机正转和反转。蜂鸣器仅在电机高速旋转时发声，其余状态保持关闭。

调试过程中，对电机速度和蜂鸣器声音进行了多次调整。电机的三档速度并非一次确定，而是根据实际转动效果逐步降低占空比，以获得更合适的转速。蜂鸣器也从单一频率改为两种频率交替的“滴露滴露”效果，使声音更符合题目中的救援提示音要求。

## 三、实现功能总结

当前 `Hardware_C1` 主要实现以下功能：

- 初始状态下，电机停止、蜂鸣器不发声、LED （除LED6）和数码管均熄灭。
- `KEY1` 循环切换电机速度：停止、低速、中速、高速。
- `KEY2` 设置电机正转，`KEY3` 设置电机反转。
- 电机高速时，蜂鸣器发出双频“滴露滴露”提示音；其他速度档位及停止状态下蜂鸣器关闭。

当前主要引脚分配如下：

| 模块          | 引脚          |
| ------------- | ------------- |
| 电机驱动 `AIN1` | `P1.0`        |
| 电机驱动 `AIN2` | `P1.1`        |
| 蜂鸣器        | `P2.5`        |
| LED           | `P2.0`        |
| 数码管段选    | `P0`          |
| 数码管位选    | `P2.2~P2.4`   |
| 独立按键      | `P3.0~P3.3`   |

## 四、关键知识点总结

### 1. 工程分层

本工程采用 `User` 和 `Driver` 分层设计。`main.c` 不直接编写底层 IO 操作，而是调用驱动函数，例如：

```c
Motor_SetSpeed(speed);
Beep_SetEnable(speed == MOTOR_SPEED_HIGH);
key = Key_Read(0);
```

这样主程序更侧重于描述任务流程，底层文件则负责具体的硬件控制。

### 2. 独立按键检测与消抖

独立按键为低电平有效。按键读取函数采用简单延时消抖，并通过静态变量 `key` 作为锁定标志，防止长按时重复触发：

```c
if (key == 1 && (KEY1 == 0 || KEY2 == 0 || KEY3 == 0 || KEY4 == 0))
```

按键按下后先锁定，待所有按键松开后才允许下一次触发。

### 3. 定时器中断

工程使用定时器 0 周期进入中断，在中断服务函数中同时处理电机 PWM 和蜂鸣器方波：

```c
Motor_Tick();
Beep_Tick();
```

这样可以使得主循环可专注于按键检测，而电机和蜂鸣器的周期性输出不受主循环执行速度变化的影响，保持稳定。

### 4. 软件 PWM

电机 PWM 周期划分为 10 等份，低速、中速、高速对应的占空比分别为：

```c
低速：2 / 10
中速：4 / 10
高速：7 / 10
```

占空比越大，电机获得的平均电压越高，转速越快。后续根据实物效果对速度进行了调整，避免低速时无法启动或高速时运行不稳。

### 5. 直流电机必须通过驱动板驱动

两线直流电机不能直接连接单片机 IO 口，因为 IO 口驱动能力不足，且电机为感性负载，直接连接可能损坏单片机。

本工程采用 DRV8833 类电机驱动板。电机两根线接至 `AOUT1/AOUT2`，单片机控制 `AIN1/AIN2`，电机电源接 `VM/GND`，且单片机和驱动板必须共地。

### 6. 蜂鸣器双频提示音

蜂鸣器由 `P2.5` 控制。关闭时统一置 `BEEP = 0`；开启后，在定时器中周期性翻转电平产生声音，并每隔约 250 ms 切换翻转间隔，形成两种音调交替的“滴露滴露”效果。

### 7. 数码管初始化熄灭

数码管底层采用显示缓冲区。初始化时将 8 位缓冲全部设置为空白码，并关闭位选，避免上电时出现残影或乱码：

```c
Seg_Buf[i] = SEG_BLANK;
```

段码表中仅保留数字 `0~9` 和空白码，当前任务无需显示字母，故不保留 `A~F` 的段码。

## 五、踩坑记录

### 1. 不能直接将不同工程混用

初期参考了已有模板，但不同工程的开发板和引脚定义不完全一致。直接复制代码易导致引脚不匹配。后续改为先确认 C1 的实际接线，再修改底层 `sbit` 定义。

经验：移植代码前，务必先确认板卡、模块和引脚对应关系，不能仅凭函数名相同就盲目合并。

### 2. LED6 亮不一定是程序主动点亮（硬件复用冲突案例）

在 `Hardware_C3` 调试中，遇到了一个典型硬件复用问题：初始状态下，蜂鸣器关闭（`P2.5 = 0`）时，板载 LED6 会亮起；若强行让 LED6 熄灭（需 `P2.5 = 1`），蜂鸣器则可能发声。经查原理图，`P2.5` 同时连接蜂鸣器和 LED6，且两者所需的电平恰好相反：

| 功能     | 所需 `P2.5` 电平 |
|----------|----------------|
| 蜂鸣器关闭 | 0              |
| LED6 熄灭 | 1              |

因此，软件无法通过同一个 IO 同时满足两个相反的电平要求，这不是程序初始化或逻辑错误，而是硬件引脚复用导致的物理限制。

经验：当发现某个 LED 状态异常时，不能只检查 `Led.c`，必须结合原理图分析该 IO 是否还被其他模块共用。若确认是复用冲突且电平要求相反，则需承认硬件限制，并在说明文档中记录，不可强行修改底层关闭电平以迁就 LED，以免破坏另一模块的正常工作。

### 3. 数码管上电乱亮需从初始化解决

动态数码管若未在初始化时清空缓冲、关闭位选，上电后可能出现短暂乱码或残影。

经验：所有显示类模块都应在 `main()` 开始时明确初始化为熄灭状态。

## 六、收获

通过 `Hardware_C1` 项目，我将此前蓝桥杯学习中积累的 51 单片机基础知识重新串联起来，实现了从“在固定开发板上调用驱动”到“自主完成引脚分配、底层封装与综合调试”的过渡。

与单独完成按键实验或蜂鸣器实验不同，本次更接近一个完整的小型项目，需要统筹考虑以下方面：

- **工程结构**：采用 `User` 与 `Driver` 分层，提升了代码的可维护性和可移植性；
- **底层驱动封装**：各模块接口独立，主程序仅关注状态流转，逻辑更加清晰；
- **定时器与 PWM**：在中断中统一处理周期性任务，保证了输出的实时性和稳定性；
- **硬件接线与调试**：从原理图确认到实物验证，培养了对硬件底层现象的分析能力。

此次最大的收获在于深刻认识到单片机开发不能仅以“代码通过编译”为目标，而必须将代码、引脚、原理图和实物现象作为一个整体进行综合分析。许多问题表面看似程序缺陷，实则源于接线错误、电平匹配不当、驱动能力不足或开发板硬件复用等因素。这种系统性的调试思维和工程化的开发习惯，将对我后续的嵌入式学习产生深远的积极影响。
